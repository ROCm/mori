# InterNode V1: bandwidth and latency per optimisation stage

Two nodes (mi355-gpu-49 + mi355-gpu-51), 8 GPUs each, EP=16, gfx950/mi355x, ROCm 7.14.60850, NIC ionic, `--kernel-type v1 --num-qp 2 --dtype bf16`, hidden=7168, topk=8. Generated by `tools/isa_probe/bw_report.py render`; raw logs in `data/run2n/`, per-stage numbers in `data/bw/`.

Latency is the grand mean over all 16 ranks and all kept rounds, then the median over passes. Bandwidth is the mean over ranks and rounds; `min` is the slowest rank, which is what bounds a collective. `default` geometry is the shipped `(B,R,W)=(96,64,8)` for both phases and is the basis for comparing kernels: it holds the launch config fixed so a change in the number is a change in the kernel. `tuned` is the best geometry found for that shape.

## What each optimisation was worth

Isolated by flipping a single `constexpr` and running A(on)-B(off)-A(on), with `|A1-A2|` as the drift bound. Kernel builds cannot be interleaved the way harness flags can, and editing this kernel at all moves latency by more than several of these are worth -- so for each one, two questions are asked separately: did total latency improve, and did it improve *at the shape where the new code can actually run*. When those disagree, the win is code generation, not the optimisation.

| # | change | state | result |
|---|---|---|---|
| opt 3 | skip known-empty chunk slots | `on` | -0.82 us (-0.26%) at T=64 cap=4096, the shape it targets. The -29.00 us (-0.85%) it also shows at T=cap=4096 is **not** this change: no slot is ever classified empty there, and the `on` build is 53 instructions and 4 VGPRs *larger*. That part is a scheduling accident. |
| opt 2 | recv shard count S | `S=8 kept` | Negative result. S is now a named constant with the constraint written down; sweeping it at fixed geometry, S=4 costs +50 us at small token counts (S*W=32 < warpSize, so each wave moves two tokens) and S=16 costs +293 us at T=cap=4096 (S*W=128 > warpSize, so half the waves poll a flag and find no payload). The shipped 8 is the optimum. |
| opt 5 | payload tile read once | `on` | **-30.07 us (-0.88%) total, -30.35 us (-1.73%) on dispatch** at T=cap=4096, and -0.52 us on dispatch at T=64 where there is little recv payload to share. Effect appears where the mechanism applies, which is the attribution opt 3 failed. |
| opt 6 | skip the saturated send-end AMO | `off` | Correctness-checked (120 varying-T rounds over cap 64/512/4096 plus a T==cap verification round: no errors, no hang). A partial A-B-A survived a contaminated window -- **+2.38 us at T=cap=4096 against a 4.49 us drift bound, -1.02 us at T=64 against 3.58 us** -- so the effect is inside the noise on both, with only one valid `off` pass at T=4096. That is the expected size for one AMO issued once per dispatch, and it is not a *stable improvement*, so it stays off. The code and the safety condition are kept; it needs a quiet machine, not more design. |
| opt 4 | parallel target resolve + slot acquisition | `not implemented` | Not done. The lane-indexed target scheme opt 5 introduced is most of the groundwork, so this is the natural next step: have lane e take its own slot instead of lane 0 taking all K_d serially. |

Optimisation 1 (launch geometry) is not in this table because it changes no code -- see `dispatch.md` for its results and, importantly, for why its tuning rule must not be applied when T < cap.

## Correctness

Every kernel change above was checked with `--cmd test` at cap 64, 512 and 4096, 40 rounds each, at a token count that varies per round -- which is what reaches partial tail chunks and uneven ranks. All ranks reported `error times: 0`. `--cmd bench` additionally verifies once per run at the geometry it is about to time, so the numbers in this file come from runs that checked themselves.

Two caveats worth keeping: the varying-T test mostly exercises opt 6's *miss* path, since a random T rarely fills every chunk slot; and an unroll-by-4 version of opt 5's tile loop miscopied (wrong recv counts, and a fault at cap=64), so the shipped form is deliberately not unrolled.

## Reproducing

```bash
# one two-node run, any harness flags
./run2n.sh <tag> --cmd bench --max-tokens 4096

# a stage of this document, then re-render it
python3 tools/isa_probe/bw_report.py measure <stage> --passes 3 --rounds 21
python3 tools/isa_probe/bw_report.py render

# isolate one kernel change: flip its constexpr, then
./tools/isa_probe/sync_kernel.sh          # push kernel sources to both nodes
./tools/isa_probe/kernel_ab.sh <arm> 3 "t4096:--cmd bench --max-tokens 4096"

# check no run sat in a window where something else used the GPUs
python3 tools/isa_probe/audit_runs.py
```
