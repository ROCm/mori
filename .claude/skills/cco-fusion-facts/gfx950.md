# gfx950 (MI355X) facts

All sources are paths in this repository, checked at commit `29e0c0868` (main,
2026-11-16). Line numbers are at that commit.

## SDMA transfers

### G950-SDMA-01: small-put latency depends on how the put is issued
- **Value:** a CU that polls a flag and then issues a put: 7.1 µs at 4 KB, 8.5 µs at
  64 KB. Packets pre-placed, the CU only rings: 5.9 / 7.3 µs. `postWaitMem`:
  4.4 / 5.8 µs. The gap is a fixed ~1.5-3 µs and is gone by 16 MB.
- **Scope:** gfx950, flag set to copy complete, median of 100.
- **Source:** `.claude/skills/cco-sdma-api/SKILL.md:355-358`
- **Label:** measured

### G950-SDMA-02: packets issued back to back by one thread cost ~2 µs each
- **Value:** gemm_ag at 8 ranks with `--chunks 4`: 28 packets from one thread took
  39-55 µs, flat across payloads differing 8x. Issuing the world-1 packets at once from
  different lanes avoids it. gemm_ar's SDMA layout states the same ~2 µs per packet,
  which is why a peer's slice is never split across queues.
- **Source:** `python/mori/ops/gemm_ag/kernels_fused.py:814-819`;
  `python/mori/ops/gemm_ar/kernels_sdma.py:50-52`
- **Label:** measured

### G950-SDMA-03: a signal (ATOMIC) packet costs about what a COPY packet does
- **Value:** with one signal per copy, 64 signalled copies take 248 µs instead of
  132 µs.
- **Source:** `.claude/skills/cco-sdma-api/SKILL.md:169-174`
- **Label:** measured

### G950-SDMA-04: put size has a knee
- **Value:** gemm_ar with 8 chunks sends 3.5 MiB per put; 16 chunks (via
  `--block-m 128`) halve that to 1.75 MiB, under the SDMA knee, and are slower. Below
  ~256 KB per put, SDMA is expected to lose to LSA (decode sizes).
- **Source:** `python/mori/ops/gemm_ar/README.md:1792-1794`;
  `python/mori/ops/gemm_ar/kernels_sdma.py:53-54`
- **Label:** measured (3.5 vs 1.75 MiB); source-reported (the ~256 KB knee)

### G950-SDMA-05: about 59 GB/s per link for a multi-MB put
- **Value:** a 7.3 MB slice ([4096, 7168] bf16) runs in "~59 GB/s territory". One peer
  is one xGMI link: one put per peer, never split across queues.
- **Source:** `python/mori/ops/gemm_ar/kernels_sdma.py:50-53`
- **Label:** source-reported

## Ordering and synchronization

### G950-SYNC-01: the counter atomic is the release
- **Value:** an `acq_rel` `atomic_add` emits its own `buffer_wbl2` / `buffer_inv` pair,
  on thread 0 only. An added `__threadfence_system` repeats that work per lane.
- **Source:** `python/mori/ops/gemm_ar/kernels_fused.py:1948-1950`
- **Label:** source-reported (from the emitted ISA)

### G950-SYNC-02: an added fence after the counter atomic
- **Value:** gemm_ar, m=16384, blockscale, 8 ranks, twice each: no fence 1143.5 /
  1144.8 µs; agent-scope fence 1797.0 / 1798.5 µs; system-scope fence 1936.1 /
  1937.5 µs. The fences cost 650-790 µs and changed nothing in accuracy (relL2
  2.350e-3 in all three).
- **Source:** `python/mori/ops/gemm_ar/kernels_fused.py:1953-1956`
- **Label:** measured

### G950-SYNC-03: an acquire per tile
- **Value:** about 90 µs of a 0.96 ms GEMM1 (example 13).
- **Source:** `examples/cco/python/13_flydsl_mega_moe_stage1_sdma/README.md:154`
- **Label:** measured

### G950-SYNC-04: a quiet inside the GEMM
- **Value:** 1.8-10.7% slower; the drain kernel does it afterwards instead.
- **Source:** `python/mori/ops/gemm_ar/README.md:1711-1712`
- **Label:** measured

## Counters and wrap

### G950-CTR-01: gemm_ag and gemm_a2a reset the chunk counter on the last arrival
- **Value:** the block whose increment completes a chunk adds `-tiles_per_chunk`, so
  the counter returns to 0 for every chunk.
- **Source:** `python/mori/ops/gemm_ag/kernels_fused.py:807-811`
- **Label:** source-reported

### G950-CTR-02: a modulo election on a running counter breaks at wrap
- **Value:** electing with `seq % tiles_per_chunk` picks the wrong tile once the
  counter crosses 2^31, or 2^32 unless `tiles_per_chunk` is a power of two.
- **Source:** `python/mori/ops/gemm_ag/kernels_fused.py:806-809`
- **Label:** source-reported

### G950-CTR-03: gemm_ar still uses monotonic counters with a modulo election
- **Value:** the counters are never reset (`kernels_fused.py:1975`) and elect with
  `seq % ready_tiles == 0` (`:1992`) and `seq % expected == 0` (`:1901`); the window is
  zeroed once, at allocation (`op.py:784`). By `G950-CTR-02` this can elect the wrong
  tile after about 2^31 increments when the modulus is not a power of two.
- **Source:** `python/mori/ops/gemm_ar/kernels_fused.py:1901,1975,1992`;
  `python/mori/ops/gemm_ar/op.py:784`
- **Label:** source-reported (the code); inferred (the hazard, untested)

### G950-CTR-04: wrap-test coverage
- **Value:** ag_gemm (`case_epoch_wrap` in `tests/python/cco/ag_gemm_op_worker.py`) and
  a2a_gemm (counters preset just below 2^32, `tests/python/cco/a2a_gemm_worker.py`)
  test wrap. gemm_ar, gemm_ag and gemm_a2a have no wrap test.
- **Source:** search of `tests/python/cco/*<op>*` for `wrap`, `epoch_wrap`, `2**32`,
  `preset`
- **Label:** source-reported (repository state)

## Compiler and ISA

### G950-ISA-01: communication code can trigger UnclusteredHighRPReschedule
- **Value:** example 11's communication role raised register pressure over the
  threshold of the AMDGPU `UnclusteredHighRPReschedule` stage, which broke the GEMM
  main loop's clustering: the MFMAs moved 23 instructions earlier and the mean
  load-to-`s_waitcnt` distance fell from 20.9 to 13.6. Cost: 8.5% of GEMM2 at 16384
  tokens per rank, even when the communication role never runs. Fix: the LLVM option
  `amdgpu-disable-unclustered-high-rp-reschedule`, kept set across the first launch
  (FlyDSL emits code then).
- **Source:** `examples/cco/python/11_flydsl_mega_moe_sdma/mega_moe_gemm2_with_sdma.py:1526-1538`
- **Label:** measured

## gemm_ar results

### G950-GAR-01: phase breakdown, DeepSeek-V4.1-Flash wo_b, TP4
- **Scope:** M=16384, N=5120, K=2048, MXFP8 GEMM, BF16 scatter and gather, 256x256
  tiles, 8 chunks, one SDMA queue per peer; mori `f3bff0ae`, node `v2-015`,
  2026-09-30.
- **Value (µs):** split-SDMA: GEMM 149.9, scatter 728.0, reduce 32.4, gather 727.8,
  whole call 1638.8. Fused-SDMA: GEMM with scatter submission 202.2, drain 587.3,
  reduce 32.5, gather 727.7, whole call 1549.6. The fused GEMM grows by 52.3 µs, the
  scatter/drain shrinks by 140.7 µs, the GEMM + scatter prefix saves 88.4 µs.
- **Caveat:** phase times are measured inside each complete pipeline; a standalone
  GEMM time cannot be substituted.
- **Source:** `python/mori/ops/gemm_ar/README.md:1277-1317,1328-1329`
- **Label:** measured

### G950-GAR-02: narrower wire, same setup as G950-GAR-01
- **Value:** moving the gather to FP8 over LSA saves 314.7 µs of the whole call. An FP8
  scatter on top adds 40.0 µs to the GEMM epilogue and saves 362.2 µs of drain,
  10.1 µs of reduce and 333.5 µs of the whole call.
- **Source:** `python/mori/ops/gemm_ar/README.md:1318-1323`
- **Label:** measured

### G950-GAR-03: on Flash TP4, fusing collects about half of the ceiling
- **Value:** for M from 4096 to 16384, fused-SDMA gains 1.4-8.7% over split-SDMA,
  against ceilings (GEMM time / split time) of 11.3-18.0%. The GEMM is about 180 µs
  against 1130-1410 µs of communication.
- **Source:** `python/mori/ops/gemm_ar/README.md:1160-1191`
- **Label:** measured

### G950-GAR-04: fused-LSA loses on Flash
- **Value:** 5.3-8.0% slower than split-SDMA at TP4 across six cells. Split-LSA alone
  is fine; LSA in the fused kernel moves bytes with the GEMM's own waves, a bad trade
  when the GEMM is about 11% of the layer.
- **Source:** `python/mori/ops/gemm_ar/README.md:1195-1200`
- **Label:** measured

### G950-GAR-05: on Flash, most of the win is the GEMM
- **Value:** mori's MXFP8 GEMM is 30.3% faster than the bf16 route before any fusion
  (an older single-call harness, hot only; 27% on the fixed timer).
- **Source:** `python/mori/ops/gemm_ar/README.md:21,561,833-840`
- **Label:** measured

### G950-GAR-06: DeepSeek-V4-Pro wo_b
- **Value:** 1146.2 µs against the model's 1419.5 µs (-19.4%) at [16384, 7168],
  K=2048, on 8x MI355X.
- **Source:** `python/mori/ops/gemm_ar/README.md:19-20`
- **Label:** measured

### G950-GAR-07: the baseline is not monotonic in M
- **Value:** the baseline retunes per M bucket and swings about 20% between buckets
  (M=8200 costs 943 µs where M=8800 costs 1133 µs), so a threshold is read from a
  dense curve, not interpolated.
- **Source:** `python/mori/ops/gemm_ar/README.md:1263-1266`
- **Label:** measured

## Measurement

### G950-MEAS-01: a single-call graph replay has a 13.40 µs floor
- **Value:** an almost empty kernel replays in 13.40 µs from a single-call graph and in
  1.51 µs amortized over 200 calls per graph.
- **Source:** `benchmark/cco/flydsl/gemm_ar/timing.py:28-30`;
  `python/mori/ops/gemm_ar/README.md:1606`
- **Label:** measured

### G950-MEAS-02: hot loops read weights from the 256 MB LLC
- **Value:** `wq_b`'s 10.5 MB weight reads at 4308 GB/s hot and 2561 GB/s cold. A cold
  ring must be longer than the graph's calls (`cold_reps = max(reps, n)`), or the
  "cold" numbers are hot.
- **Source:** `benchmark/cco/flydsl/gemm_ar/timing.py:35-37`;
  `python/mori/ops/gemm_ar/README.md:1613-1633`
- **Label:** measured

### G950-MEAS-03: one shape per process
- **Value:** M=4200 and M=4700 (both padded to 5120) read 697 µs and 1083 µs in one
  process; isolated, both read 697 µs.
- **Source:** `python/mori/ops/gemm_ar/README.md:1646-1649`
- **Label:** measured

### G950-MEAS-04: an eager benchmark is biased against the fused path
- **Value:** before `_PinnedLaunch`, 181.6 µs of per-dispatch Python sat on the critical
  path; the eager harness read the bf16 wire at +11.0% where the graph-replaying
  server read -2.3%.
- **Source:** `python/mori/ops/gemm_ar/README.md:1635-1644`
- **Label:** measured

### G950-MEAS-05: a silent non-fusing path looks like a slow one
- **Value:** a mis-read weight shape made the op fall back to the split path without a
  word; only an assertion that fusing happened catches it.
- **Source:** `python/mori/ops/gemm_ar/README.md:1651-1659`
- **Label:** source-reported

### G950-MEAS-06: gemm_ar's timing protocol
- **Value:** 8 calls per graph, 21 replays, 3 alternating rounds (5 for short tails).
- **Source:** `python/mori/ops/gemm_ar/README.md:640`
- **Label:** source-reported

## Environment

### G950-ENV-01: without `BUILD_CCO_SDMA`, every put silently does nothing
- **Value:** the result is wrong rather than an error. `GemmAllReduceOp` and
  `GemmReduceScatterOp` do not check at construction; `self_test()` is the guard.
- **Source:** `docs/MORI-CCO-FUSED-OPS-GUIDE.md:83-90`;
  `python/mori/ops/gemm_ar/README.md:1666`
- **Label:** source-reported

### G950-ENV-02: gemm_ag's fusion threshold
- **Value:** `mode="auto"` fuses where `ceil(M/256) * ceil(N/256)` is at least the CU
  count: a GEMM long enough for the transfer to hide under.
- **Source:** `docs/fused-gemm-ag.md:162,242,339`
- **Label:** source-reported

### G950-ENV-03: peer memory can land in host memory
- **Value:** on kernels without `CONFIG_DMABUF_MOVE_NOTIFY` (with an amdgpu build that
  checks it), HIP VMM peer memory is pinned into host memory instead of peer VRAM;
  mori-cco shows a ~9x slowdown or hangs.
- **Source:** `.claude/skills/known-issues/SKILL.md` (issue 1)
- **Label:** source-reported

### G950-ENV-04: ROCm 7.2.x puts uncached VMM allocations in the coarse-grained pool
- **Value:** cco combine is about 10-15 µs slower.
- **Source:** `.claude/skills/known-issues/SKILL.md` (issue 3)
- **Label:** source-reported

### G950-ENV-05: back-to-back 8-rank runs can fail to start
- **Value:** `hsaKmtCreateQueueExt` fails while the previous run's ranks still hold
  their SDMA queues. About 10 s between runs is enough; a leftover server holding
  queues is not.
- **Source:** `python/mori/ops/gemm_ar/README.md:1675-1678`
- **Label:** measured
