You own SDMA compute-communication fusion in mori. Goal: a measured, reproducible, correct gain with the fewest assumptions and the least code.

## Core model
Every fused op here is one pipeline per chunk: **produce → publish → transfer → land → consume**. Fusion overlaps the transfer of one chunk with producing or consuming the other chunks. The ops differ in one point only: the side the GEMM is on.
- **GEMM produces** (GEMM + AR / RS / AG / A2A, GEMM2 + combine): chunks become ready tile by tile inside the GEMM; a later kernel (reduce, next layer) consumes them.
- **GEMM consumes** (AG / A2A + GEMM, dispatch + GEMM1): the data is ready before the GEMM (or arrives from a dispatch); GEMM tiles wait for their chunk.
Design each stage with the rules below, then fill in the instance table. Deviate from a rule only on a measurement.

## Core design
1. **Layout: one contiguous run per (source, destination).** The copy engine cannot gather. Pick the shard axis so each pair's data is one run of whole tiles, at the same offset in every rank's window. If the natural layout is strided, stage it in the producer's epilogue, or let the producer write straight into the window (zero copy). Metadata that is per row (ptpc scale) travels with its rows; metadata that is K-block-major (blockscale, mxfp8) is strided and needs its own put. CU stores into the window are local and coalesced (stage through LDS, 16 B per lane: 114.3 → 73.4 µs). Their cache policy is per op: cached, released by the counter atomic (`gemm_ar`) or by a one-wave system fence (`gemm_a2a`); `sc0 sc1` plus a thread-0 release fence in `gemm_ag` (its default `sc_release`: `fence="release"`, `peer_uncached=True`), write-through alone in the MoE examples. Write-through is free when nothing local re-reads the data (`gemm_ar`'s reduce: 1153.4 → 1148.7 µs). Write-through stores straight to a *peer* gave wrong results (relL2 ~1.7e-2, cause unknown).
2. **Chunk: the unit of overlap.** A chunk overlaps only the work still to come on the other side. Order the work so that:
   - work on own data runs first (it never waits);
   - the rest runs chunk-major, peers rotated by rank, so no two ranks hit one peer first and the first wave needs only chunk 0;
   - the producer's completion order and the consumer's need order are the same order.
   Size: one chunk per workgroup round of tiles. Rounds come from the grid — `gemm_ag`'s `pick_chunks` takes `max(1, tile_grid(m, n, tile) // cus)`, which residency can only lower — and every op then caps the count, because a queue per chunk per peer is what runs out of engine slots: `gemm_ar` 8 (the measured knee), `gemm_ag` 4, `gemm_a2a` 8 with each put ≥ 1 MiB, `ag_gemm` / `a2a_gemm` 16 (the window's slots). Take the cap seriously; without it the plan walks past the queue budget. Each chunk adds a fixed overhead (idle link: ~47 GB/s in one chunk, ~33 GB/s in eight), so use the largest chunks that still overlap. A chunk cannot complete before the wave that computes it. Log the chunk count each run used (a knob silently fell to 1 chunk: +5.5%).
3. **Publish: the poster is the first agent that knows a chunk is complete and is sure to run.**
   - GEMM produces: after its stores retire (`s_waitcnt vmcnt(0)` + barrier), one thread per block does one counter atomic. Whether that atomic is itself the release is per op (rule 1): in `gemm_ar` it is, via its `buffer_wbl2`/`buffer_inv` pair on thread 0; `gemm_a2a` adds a one-wave system fence, and `gemm_ag` adds a thread-0 release fence and spreads the atomics over world−1 lanes. The block whose increment completes the chunk posts it ("last finisher"; see rule 7 for the counter's state). No comm workgroup. An extra fence here cost 90 µs (440 → 350) to 650–790 µs (`gemm_ar` M=16384, blockscale, P=8, per-lane).
   - GEMM consumes, data ready before it: block 0 of the GEMM posts (it is dispatched first, so it cannot starve). Not a kernel on a second stream: waiting tiles fill the CUs and an undispatched poster never runs.
   - Data ready at run time (MoE): a dedicated comm workgroup polls the counters at agent scope with one agent acquire per chunk (example 11: `spin_until_ge_i32_agent` + `fence_agent_acquire`) and posts each complete chunk; example 13 instead posts after a grid rendezvous, and keeps its relaxed system-scope poll for the receiver-side layout wait. It holds a CU slot even when idle, so give the persistent grid all CUs (example 11: the last CU finished 3.3% late at `persist_cu=192`; all CUs cut the overhead over GEMM2 by a third, 0.200 → 0.133 ms).
   For every poster: one issuer per peer, so the peers' queues run concurrently — a lane each where the poster is a block that also computes, a wave each whose lane 0 issues where it is a comm workgroup (one thread issuing 28 puts serially took 39–55 µs; the ~2 µs is the engine's cost per packet, not the issue — 64 packets issue in 1.3 µs); a poster that also computes defers its own `quiet` past its tile (`quiet` first: 51 µs over gemm-only; after: 9 µs); only `ag_gemm` also takes a tile nothing waits on, `a2a_gemm`'s block 0 still takes the last one.
4. **Transfer: one queue per (source, destination) link, all links at once.** The peer links run concurrently, so send to every peer in parallel; no ring (MI355X has one xGMI link per peer). More queues or engines per link are slower (`a2a_gemm`, 1 / 2 / 4 queues: 251.8 / 256.3 / 266.2 µs). Chunks of one link share its queue (a lock serializes the issue; it is a test-and-set spin; two unexplained hangs, lock suspected, never reproduced in 100+ runs) or take one queue each when lanes post in lockstep (a lock would deadlock). The copy engine moves raw bytes only: a step that converts or reduces is better as a CU pull after the GEMM (pull 957.3 vs SDMA 1018.9 µs).
5. **Land: the consumer learns arrival from a signal, not from a wait on the sender.**
   - Signal each chunk with a trailing remote signal on the same queue: seeing the count means the bytes landed. Not `quiet` + flag store per chunk (it idles the engine: 199.1 → 190.2 µs).
   - Consumer in the same kernel: thread 0 spins on its chunk just before the first load. cco windows are uncached by default (`CCO_UNCACHED_WINDOW`), so no acquire is needed (full fence 187.5, acquire 151.8 µs, none correct) — but check three things before relying on it: the uncached default needs HIP newer than 70051831, or `cco_init` falls back to pinned memory; `a2a_gemm` ships `acquire="inv"` and `ag_gemm` always acquires, so `none` is a measured choice rather than the shipped one; and in `a2a_gemm`'s `segment` mode every wave spins, not just thread 0. With `CCO_UNCACHED_WINDOW=0` add `buffer_inv`. One receiver wave that polls every source and feeds a ready queue (example 13's opt-in `--ready-first`) gains with tiles per worker but has a fixed cost (−85 µs at bs 2048, +11 µs at bs 256): the default is a static per-tile wait on the signal counters, which wins at small batch.
   - Consumer in the next kernel: finish in a one-block tail kernel, lane p for peer p: `quiet_queue` on every queue that carried peer p's chunks → system fence → store this call's epoch into peer p's flag → spin until p's flag in my window reaches it. The kernel boundary orders the data. No `quiet` inside the GEMM (gcnasm measured 1.8–10.7% slower; external).
6. **Memory order: one release per block, none in a loop, in the writer's kernel.** Keep `buffer_wbl2` / `buffer_inv` out of tile and poll loops (one acquire per tile: 90 µs of example 13's 0.96 ms GEMM1; per-lane fences grow with the square of the block count, inferred). CU-written data that a peer reads is fenced in the kernel that wrote it: a fence in a one-block kernel writes back one XCD's L2 of eight (2–3 correct in 6 → 10/10).
7. **Epochs and reuse: every call is a fresh launch, and no rank refills a slot a peer still reads.** Flags and signals are running totals advanced by the kernels, never reset by the host. Compare them wrap-safe (`(int32)(cur - target) >= 0`), as `gemm_ag`, `ag_gemm` and `a2a_gemm` do; `gemm_a2a`'s `_credit.py` and `gemm_ar`'s `kernels_lsa._spin_until` still compare unsigned, which passes at once on the call whose flag wraps — and both tail barriers use those spins. A chunk counter is either monotonic (`gemm_ar` elects on `seq % tiles_per_chunk`) or reset on the device by the last finisher (`gemm_ag`, `gemm_a2a`); do not reset one from the host. A (source, queue) signal slot carries one user. An end-of-call barrier proves every peer *wrote* call e−1, not that it *read* it. So: when the output is the receive buffer, post credit `e` to every peer at call start and wait for peer d's credit before the first put to d; when a later reader (reduce, GEMM) reads slots the next call refills, close each call with a barrier-only kernel after the reader. Without the guard: relL2 0.7–1.3.
8. **Fuse only when the other side can hide the transfer.** The most fusion can save is about `gemm / split`; fusion collected about half of it. It needs work left to overlap: at least 2 workgroup rounds and one chunk per round, so the fused tile is often not the split tile (`gemm_ag`: one round ran ~1% behind split; `gemm_ar` K3 blockscale: crossover M ≈ 2048). On the consumer side a waiting tile holds its CU (P=8: ~50 µs idle per CU), so it wins most where `1/P` of the work is local and large. When the transfer is several times the GEMM, first cut the bytes (fp8 wire, or a different op order: `gemm_ag` −60% bytes for −61% latency), then fuse. Floor for a static chunk-major consumer: the last chunk the first wave needs, plus the remaining tiles; get past it only by posting before the GEMM starts (from the producer of the operand) or by giving the first wave work that does not wait.

| Op | GEMM | Run per destination | Poster | Land / guard |
|---|---|---|---|---|
| GEMM + AR / RS (`gemm_ar`) | produces | row band of C | last finisher; chunks share the peer's queue | tail kernel; reduce (+ gather) kernel; barrier after the reduce, `rs_barrier` for RS |
| GEMM + AG (`gemm_ag`) | produces | C rows in own recv slot | last finisher; lanes in lockstep, one queue per chunk | tail kernel; recv-reuse credit |
| GEMM + A2A (`gemm_a2a`) | produces | `[dst][M][N/P]`, staged in the epilogue | last finisher; chunks share the peer's queue behind a lock | tail kernel; recv-reuse credit |
| AG + GEMM (`ag_gemm`) | consumes | own row bands | block 0 | per-band flag (`quiet` + store; signal untested here); closing barrier |
| A2A + GEMM (`a2a_gemm`) | consumes | per-source K segment of `[P·M, K/P]` | block 0 | per-band signal; waits per segment, per tile at P ≥ 8 and M ≥ 4096; closing barrier |
| GEMM2 + combine (example 11) | produces | per chunk | comm waves in the GEMM, one per peer, on per-chunk counters | per-peer flag + one trailing signal per call |
| dispatch + GEMM1 (example 13) | consumes | per chunk | comm workgroup, after a grid rendezvous | per-tile wait on the signal counters (ready queue opt-in) |

## Measured on MI355X (8 GPUs, xGMI)
- A put costs about 3 µs + bytes / 61 GB/s on one queue — a fit to the `cco-sdma-api` skill's table, which states ~2 µs per packet and a ~6 µs fixed dispatch cost. A trailing signal ATOMIC adds about 2 µs (64 puts: 132 → 248 µs). Puts on one queue run one after another. Per link: 53.7 GB/s scattered against a 76.8 GB/s line rate; 410–470 GB/s out per GPU over 7 links.
- The copy engine is not slowed by the GEMM; the GEMM is slowed by the transfer (tiles 47.5 → 56 µs, ~18%) and by the fused protocol (GEMM +52.3 µs, drain −140.7 µs). Time the GEMM inside the pipeline, not standalone.
- A release fence writes back this XCD's L2 (`buffer_wbl2`, one of eight); an acquire invalidates it (`buffer_inv`).
- Cross-device access is uncached: the cost is serialized round trips, not bytes. Spread peers over lanes (one thread walking 8 destinations serializes 16 round trips, ~10 µs). A pull (xGMI read) grid needs about a tenth of a local grid (48–80 blocks beat 512: 959 vs 1184 µs).
- CU peer stores (LSA) reach 58–60% of line rate against 75–81% for the copy engine; fused-LSA was 16–19% behind split SDMA, 99% stall.
- Role code in a GEMM kernel can trigger `UnclusteredHighRPReschedule` and break the K-loop schedule (+8.5% on example 11's GEMM2 at 16384 tokens per rank). Confirm with the K-loop ISA check, then wrap the compile *and the first launch* in `llvm_options({"amdgpu-disable-unclustered-high-rp-reschedule": True})`, since FlyDSL emits code on that launch. It is a global LLVM option, not a kernel attribute, and the JIT cache key cannot see it, so toggle it only with a fresh `FLYDSL_RUNTIME_CACHE_DIR` (on another kernel: no ISA change).
- A grid barrier needs every block resident at once (767 WGs of 512 threads deadlocked: two fit per CU). cco window offsets are 64-bit; the 32-bit limit is the kernel's own buffer resource (FlyDSL scales a `buffer_load/store` offset in i32, so < 2 GiB per descriptor), so keep each buffer-addressed region inside it or rebase the descriptor. The window cannot grow: size it from `window_bytes_for(...)` and `m_max`. An engine-side wait (`post_wait_mem`) is released by a system-scope store, a peer put or signal, or a host write.
- Half the blocks also halve the per-block release and counter cost. Tile rules fitted at P=8 do not transfer to P=4.

## Measured, no gain (do not retry without a new premise)
This is an index, not the evidence: each entry sits in the README of the op that measured it, with its shape and premise. Confirm there before you retry one.
- Transfer: CU peer stores (push, or per-tile stores in the epilogue) instead of the copy engine *for raw bytes* — not a converting pull, which wins (rule 4); more queues per link; ring all-gather (rejected by argument in `ag_gemm`, not measured).
- Chunk: a short final chunk (no gain in AG; it helps only ragged AR tails: −24% at M=11264); uneven chunks; a dynamic arrival-ordered layout (90 µs behind); local-first rows (first tile 10–25 µs earlier, tiles ~4% slower).
- Publish / land: one counter per chunk with wave broadcast; per-chunk ready counters instead of the rendezvous; `quiet` + flag per chunk.
- Overlap by other means: two-stream macro partitions (5.6–10.1% slower); own-K-first as two kernels with fp32 partials; slowing compute (LDS reservation, small tiles) to create overlap; BLOCK_M=128 (GEMM 15% slower); persistent GEMM tiles (`scf.for` spills 38 VGPRs, ~2x); fusing a prepare kernel into the GEMM under a graph (±1%: the launch gap is already ~0); folded reduce + quantize (+20 µs) or grouped (2.4–4.3% slower).

## ISA check (after every kernel change, before any timing)
Dump with `FLYDSL_DUMP_IR=1 FLYDSL_DUMP_DIR=<dir>` and a fresh `FLYDSL_RUNTIME_CACHE_DIR`; read `*_final_isa.s`. Diff it against the previous version and against the same kernel without the communication role.
- **Resources**: VGPR / SGPR / AGPR counts, scratch (spill) = 0, LDS bytes. Blocks per CU must still fit the grid (a grid barrier deadlocks otherwise). VGPR headroom decides: removing 12 loads was slower (33.32 → 33.96 µs) through register moves and re-materialised addresses, with the 254 → 256 step a side effect.
- **Cache ops**: count `buffer_wbl2` and `buffer_inv`, and find where they are. Expect one pair per counter atomic, on thread 0. Locate each loop by its back edge (a branch to an earlier label); no cache op may sit between a tile loop's or a poll loop's label and its back edge. A total count alone hides a cache op inside a loop.
- **K loop**: same MFMA count and the same order. Compare the ordered instruction stream, not the set of instructions: the position of the first MFMA, and the mean distance from a load to its `s_waitcnt`. A shorter distance means the scheduler lost latency hiding. `vmcnt` retires in issue order: a load issued after the tile prefetches makes its consumer wait for them too (`gemm_ar` mxfp8 scale loads: 15–20% slower, and prefetching one K step ahead recovers 1–11% only at K ≥ 4096, costing 1–8% at short K).
- **Communication code**: window stores carry the op's own cache policy (rule 1), so check them against that op rather than against `sc0 sc1`; poll loops use the scope that op polls at and `s_sleep`, with no `buffer_inv` inside.

## Rules
- **cco SDMA API**: the `cco-sdma-api` skill owns the device API (put / get / quiet / waitSignal / commit); read it instead of restating it. It holds `reqs.sdmaQueueCount` (default 2, cap 8, fixed by the first `ccoDevCommCreate`), that a window is addressed by LSA rank and not world rank, and the 256 KB − 32 B per-queue limit before a `commit`.
- **FlyDSL**: compile-time switches use `const_expr`. The JIT cache key hashes the toolchain, the function source and its same-directory dependencies, and the closure scalars — not the kernel name. So put a scalar `repr` of any dict or object config into a closure the kernel reads (example 13's `ARENA_KEY`), and bump a scalar version when a helper in another directory changes. Naming the variants is still worth it for dumps and profiles; give each its own `FLYDSL_RUNTIME_CACHE_DIR`. A stale cache shows up as wrong results or hangs. `range(...)` must appear literally in the `for`. A `CachedWindow` cannot cross an `scf.if`; compute addresses before the branch.
- **SDMA on**: build with `BUILD_CCO_SDMA=ON` and run with `MORI_ENABLE_SDMA=1`. Without both, every put silently does nothing and the fused path reads *faster*. Call `self_test()` on every rank, check every output row from every source rank, and assert that the fused path ran (log the shapes and chunk counts served).
- **Attribution**: mark every claim not measured on the target code as "inferred". Before you say a mechanism transfers to another design, check each premise it depends on (asynchronous? occupies CUs? how many fences and grid barriers? same direction: GEMM produces or consumes?).

## Workflow
1. **Contract**: before any work, write down the objective, the shapes and dtypes, the correctness rule, the baseline (its fastest configuration and versions), the target metric, the validation and evaluation commands, and the promotion criteria (step 8). Take the defaults from the repo: validation `tests/python/cco/test_<op>*.py`; evaluation `benchmark/cco/flydsl/<op>/`; baseline the bench's `split-sdma` / `split-rccl` mode; metric the max over ranks of the per-rank medians. Return to the caller only when the objective, the shapes or the GPU host is missing.
2. **Bound it**: run local-only (no communication) and spin-only comm-workgroup references, and compute `gemm / split`, to find the maximum possible gain. If it is below noise, stop. If the transfer dominates, check first whether a better tile, fewer wire bytes or another op order is worth more than fusing.
3. **Draft**: write `.claude/drafts/<op>-<topic>.md` before any code (not under `docs/`: the docs build runs `-n -W` and fails on a page outside the toctree). Include the baseline and how it is validated, the main risks, the candidate designs ranked by expected gain and risk, the first steps, and the evidence needed to keep, revise, or reject each candidate.
4. **Off the GPU**: code, static checks, plain-Python simulation. New features are off by default, behind a switch.
5. **On the GPU**: smoke (one config, graph) → ISA check (above) → correctness → A/B.
   - Correctness: poison buffers, compare bit for bit. Run back-to-back calls with no host sync, each with its own operands (identical operands hide a stale read), and one rank held before a call; a no-guard negative control must corrupt. A lossy path needs a tolerance with a lower bound too (proves the lossy path ran); otherwise gate tight (3e-3, not 5e-3) and require three identical runs. An RCCL baseline is not bit-comparable (it adds partials in bf16).
   - Treat a hang or an intermittent wrong result as a finding: one "chunk race" was a GEMM `s_waitcnt` under-count.
6. **Measure**: take the commands and the modes from `docs/fused-tests-and-benchmarks.md`, and the ways these benchmarks have already given wrong numbers from `gemm_ar/README.md` "Measurement traps" (one-call graph floor, LLC-hot weights, eager bias, a sweep in one process, a coarse M grid, a silently non-fusing path). On top of those: report the max over ranks of the per-rank medians; ≥3 interleaved rounds; do not align rank start times with all_reduce (inferred, no measurement in the tree); compare against the fastest baseline, which may mix vendors (Torch GEMM + SDMA); record the baseline and FlyDSL versions; re-run an outlier before you use it.
7. **GPU hygiene**: one job per node; GPUs idle before a run (a neighbour cost 9% on a pure GEMM and changed the best chunk count); a timeout on every run, then kill the workers by pid. Pace the runs: 10 s between 8-rank ones per `gemm_ar/README.md`, though its tests wait 20 s, and discard the runs after a `pkill -9` (README:1429-1433, outside "Measurement traps"). If a box is slow or hangs with nothing wrong in the code, read the `known-issues` skill before you measure.
8. **Decide** for each candidate, and record the reason with numbers:
   - ISA check fails (spill, cache op in a loop, K-loop schedule lost) → **revise**.
   - Wrong results → **revise**; **reject** if the cause is the design, not a bug. Bit-exact is the rule against a same-arithmetic reference at the same tile; when the change alters the arithmetic (an RCCL baseline, an fp8 wire, a different tile) use the op's bench relL2 gate and require identical results across runs.
   - Gain below max(1%, the spread across rounds of both arms), or not the same sign in every round → **reject**, record it, and stop this direction. Use 5 rounds when the margin is under twice the spread.
   - All checks pass → **keep**. A candidate that wins at some shapes and loses at others is kept behind an M threshold, as `gemm_ar` does.
