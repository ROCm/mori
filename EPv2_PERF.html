EP V1 vs V2 Inter-node Performance (DeepSeek-R1 on MI308X, MI300X and MI355X)

This compares the inter-node dispatch/combine performance of MORI EP V1 and V2 for the DeepSeek-R1 shape on three GPUs: MI308X, MI300X and MI355X. Section 1 is the test setup, section 2 the overall results, and section 3 the per-bucket data for each GPU.

1. Test setup

1.1 Common settings

  • Shape: 256 experts, top-8 per token, hidden 7168. EP16: two nodes × 8 GPUs.

  • Workload: uniform routing, buffer capacity equal to each call’s token count, no scales, no quantization. Combine is BF16; dispatch is measured in both FP8 and BF16. FP8 is OCP e4m3 on MI355X and e4m3 fnuz on MI308X and MI300X. T is the number of tokens per rank per call, from 4 to 4096.

  • Kernels: for T ≤ 512 the LL kernels are compared (V1 InterNodeV1LL vs V2 InterNodeV2LL), and for larger T the normal kernels (V1 InterNodeV1 vs V2 InterNodeV2), matching the switch point of V2’s internode_kernel="auto". Every row compares kernels of the same family.

  • V1: SHMEM backend with num_qp_per_pe 2. That is the default of the V1 tuning script (examples/ops/dispatch_combine/test_dispatch_combine_internode.py), and V1’s tuning tables were tuned with it; the V1 API default is 1. Geometry is chosen from V1’s tuning tables by MORI_EP_LAUNCH_CONFIG_MODE=AUTO; the rules actually used on each GPU are listed in section 3.

  • V2: HIP backend with the default num_qp_per_pe of 8. The geometry and each bucket’s active QP count come from the tuning tables in python/mori/ops/dispatch_combine_v2/tuning_configs/.

  • Timing: both sides use the same data and correctness checks. Each measurement is 3 passes × (20 warmup + 30 timed rounds), dropping the first round of each pass, and latency is the mean. V1 and V2 are measured alternately three times, and each cell is the median of the three; runs that stalled throughout were discarded or re-measured. The D+C change compares the medians of each run’s D+C latency, not the sum of the D and C medians shown, so it can differ from a change computed from those cells; the largest difference is MI308X FP8 T4096 (−22.4% here, −25.1% from the D and C cells). Every run used here passed the correctness checks.

  • Bandwidth: as in V1, the mean over ranks and rounds of “bytes / time”, not the NIC line rate. The two variants differ only in how bytes are counted:

    • XGMI bandwidth counts the tokens this rank received.

    • RDMA bandwidth counts token × destination node, the local node included; for LL every token counts all nodes. With two nodes, about half of it actually crosses nodes.

    • Both sides move the same bytes in a cell, so a bandwidth change roughly mirrors the latency change. It is not the exact inverse, since bandwidth is a mean of per-round bytes / time and each cell is its own median; in two MI308X cells (FP8 T4096 combine, BF16 T2048 dispatch) both changes are negative, so the latency change favors V2 and the bandwidth change V1. In every row the XGMI and RDMA changes differ by less than 1.5 percentage points.

  • V2 is faster in every bucket on all three GPUs. No cell has a higher V2 D+C latency than V1.

  • The gain is largest at small batch. Small batches are 18%–43% faster; medium and large batches usually 7%–22%. FP8 large batches on MI308X and MI300X gain more (22%–38%), mostly in dispatch: on MI308X the two tuning tables themselves differ that much, and on MI300X V1 runs rules tuned for MI308X.

  • Small batches gain mostly in combine. At large batch it varies by GPU: FP8 on MI308X and MI300X gains mostly in dispatch; BF16 on MI300X and both dtypes on MI355X gain in both phases, by 8%–27% and 5%–18% respectively; MI308X’s combine is within 7% of V1 except at T2048.

  • Treat the MI308X small-batch numbers with caution. At T ≤ 32 V1 runs much slower than its own tuning table records; going by the two tables, V1 is the faster side at T ≤ 32, with V2’s FP8 D+C 3%–8% higher. See 3.1.

  • Bandwidth is listed for large batches only. Small batches are latency-bound, and their bandwidth change only mirrors the latency change.

  • Part of the gap comes from rules V1 never tuned. V1 has no BF16 dispatch rules for H7168 on MI308X and only some on MI355X, and V1’s MI300X table has only LL rules for T ≤ 64; the MI308X rules the normal kernel borrows are too small for MI300X. See section 3.

  • This is a kernel-level comparison, not end-to-end inference. Only this one shape with uniform routing was measured; real workloads route unevenly and run expert computation between dispatch and combine.
