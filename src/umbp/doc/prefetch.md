# Unified prefetch to local DRAM

Prefetch prepares a readable, committed copy on the target UMBP node before a
normal LOAD needs it. It does not copy into an Engine's GPU buffer. The normal
GET/ranged GET and the standalone shared-memory registration protocol still
perform that step.

Both APIs use one coordinator in `PoolClient`:

* `BatchPrefetch(keys)` / Python `batch_prefetch(keys)` is a background hint.
  Its integer result is the number of input keys **admitted**, including keys
  joining existing work. Admission does not promise a hit or completion.
* `SubmitPrefetch(keys, options, request_id)` / Python `submit_prefetch(...)`
  returns admission and a request ID immediately. `GetPrefetchStatus(id)` /
  `get_prefetch_status(id)` returns progress, per-input results, and timing.

Already-local DRAM keys are validated and leased. Local SSD keys follow the
source tier's weighted DRAM order, then promotion targets above that tier;
the SSD source remains intact. Remote keys use Master routing and batched
whole-object pulls into the policy's ordinary placement order, filtered to
DRAM, with capacity fallback between eligible backends. A failed remote
transfer is rerouted once, excluding its original source. Local SSD copying
and remote pulls overlap for a mixed request.

Duplicate keys within or across outstanding requests share the same operation.
Results retain input order and duplicates. Engine hints, Router requests and
reactive ranged-read locality prefetch all use this operation table.

## Tracked API

```cpp
PrefetchOptions options;
options.timeout = std::chrono::milliseconds(2000);
options.lease_ttl = std::chrono::milliseconds(1000);
auto submitted = client->SubmitPrefetch(keys, options, "request-123");
// Forward the model request once accepted. Do not wait for READY here.
if (submitted.accepted) {
  auto status = client->GetPrefetchStatus(submitted.request_id);
}
```

```python
submitted = client.submit_prefetch(
    keys, timeout_ms=2000, lease_ttl_ms=1000, request_id="request-123"
)
if submitted.accepted:
    status = client.get_prefetch_status(submitted.request_id)
    # status.state, status.results[i].ok/code/source/backend_id/bytes,
    # status.completed_keys, status.lease_remaining_ms
```

An empty ID is generated by the server. Repeating an ID with the same keys and
normalized options returns the same task; a different payload is rejected.
Zero timeout/lease selects the defaults: 5 seconds for execution and 500 ms
for the lease. Each duration is limited to 5 minutes. The execution deadline
starts at acceptance, including queue time. A subscriber timing out does not
cancel another subscriber or free an in-flight transfer's destination.

| State | Meaning |
| --- | --- |
| UNKNOWN (0) | No retained record, including records past retention. |
| QUEUED (1) | Accepted; none of its operations has started. |
| RUNNING (2) | Some work has started; final protection is not yet complete. |
| READY (3) | Every input key was committed in DRAM and leased before the deadline. |
| PARTIAL (4) | All operations finished before the deadline; some keys could not be prepared. |
| FAILED (5) | No key could be prepared, or Clear/Shutdown invalidated the task. |
| EXPIRED (6) | The submission deadline elapsed before task completion. |

`completed_keys` counts successful input positions, including duplicates.
`results` provides a reason such as missing, no eligible DRAM, no capacity,
transfer/commit failure, fragmented destination, expired, or no longer resident.
Partial progress is observable while RUNNING. EXPIRED preserves observed
completion information but provides no task lease guarantee.

Before a task becomes READY/PARTIAL, every successful key is revalidated and
its lease renewed. Early copies that disappeared while other keys were copying
are downgraded. The lease is independent of the execution deadline.
`lease_remaining_ms` is sampled on the server, conservatively measured from
final validation; callers must also allow for RPC transit time. A
historical READY record with zero remaining lease does not promise residency.
Read leases never shorten an existing reader's protection.

GET/ranged GET wait only on relevant outstanding keys, using one bounded wait
for the batch, then execute their ordinary read path. The existing
`UMBP_EXPLICIT_PREFETCH_WAIT_TIMEOUT_MS` setting is retained (default 5000 ms,
maximum 300000 ms; zero disables waiting).

## Router and standalone compatibility

The deployed experimental Router's request/status wire contract is retained:

* `/umbp.UMBPStandalone/SubmitPrefetch`
* `/umbp.UMBPStandalone/GetPrefetchStatus`
* Request fields: `keys=1`, `lease_ttl_ms=2`, `timeout_ms=3`, `request_id=4`.
* Submit fields 1–3, status fields 1–8, and state values 0–6 are unchanged.
* Status fields `results=9` and `lease_remaining_ms=10` are additive.

`UMBP_PREFETCH_CONTROL_ADDRESS=host:port` enables the existing optional TCP
listener. It shares the standalone service and its insecure gRPC credentials;
deploy it on the same trusted network as the existing UMBP control plane.
The Engine retains its UDS and FD handoff. Router worker targets, key templates,
block size, max keys, timeout and lease configuration do not change. The Router
continues to submit after choosing a worker and forward after acceptance.

`Ping` advertises `supports_async_prefetch` and `prefetch_hint_version=1`.
New forwarding clients fail explicitly when async prefetch is unsupported and
only send the count-returning hint when its protocol version is advertised.
The #823 `BatchKeysRequest -> CountResponse` method remains available to #823
clients. The older experimental synchronous
`PrefetchRequest -> BatchBoolResponse` is a different protocol and is not
supported under that same method name; requests carrying the legacy option
fields are rejected. Keys-only requests are indistinguishable on the wire, so
legacy synchronous clients must migrate to Submit/Status.
The deployed Router does not call that synchronous method.

No SGLang queue hook is introduced here. Existing hint callers and the current
Router can use this core without changing the Engine data path.

## Bounds, cache policy and lifecycle

The coordinator defaults to 1024 retained tasks, 4096 input keys per task,
8192 queued/running unique keys, 65536 retained input positions, and 64 MiB of
retained key strings. Keys are limited to 4096 bytes and IDs to 256 bytes.
Terminal tracked records are retained for 5 minutes; completed hint records
are immediately discarded. Two workers each batch up to 128 unique keys.
Remote destination allocations are limited to 128 MiB per worker per batch;
larger individual objects are declined. Remote size/admission policy also
applies. Clear stops admission, drains real work, clears storage and resumes;
Shutdown joins the workers before destroying backends or transfer engines.

`prefetch_budget_bytes` (Python `UMBPDistributedConfig.prefetch_budget_bytes`,
standalone `UMBP_DISTRIBUTED_PREFETCH_BUDGET_BYTES`) retains #823's semantics:
zero disables explicit prefetch/hints; a positive value budgets temporary
SSD-to-DRAM copies. The default is 16 GiB. Lease/read-protected copies remain
accounted for and may temporarily exceed this soft budget. Remote copies are
ordinary cache residents. The independent `ranged_locality_prefetch` switch
continues to govern reactive prefetch after a ranged read.

The whole-object remote executor requires a contiguous destination in one MR.
A scattered/cross-MR allocation is aborted and reported as FRAGMENTED if no
other eligible backend can accept it. This does not change normal ranged I/O.

`mori_umbp_prefetch_events_total{event=...}` records accepted/rejected requests,
joined input keys, successful/failed terminal input keys, expired requests and
GET wait timeouts. Request IDs are not metric labels. Per-request queue,
execution and total latency accompany status; existing tier-copy and re-cache
statistics retain their byte/installation accounting.

## Validation

CPU tests cover the coordinator's shared completion, independent workers,
deadlines, leases, queue/table limits, idempotence, exceptions and drain;
weighted/mixed SSD tier behavior; and standalone IPC with Router-compatible
wire bytes. A masterless test writes actual SSD backend files, submits a mixed
SSD/missing request and checks the resulting DRAM bytes while retaining the SSD
source. `test_prefetch_remote` uses the real destination backends and a
simulated transport for allocation, commit, abort, capacity fallback,
cross-buffer rejection, bytes read back through GET, and publication timing.
Build that transport-seam test with `-DMORI_UMBP_TESTING=ON`; all linked UMBP
objects must use the same setting.

Real multi-node RDMA, mixed SSD/RDMA performance and SGLang TTFT/throughput
measurements require a separate hardware run. CPU transport simulation does
not establish those results.
