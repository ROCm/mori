# EP V1 与 V2 跨节点性能对比（DeepSeek-R1，MI308X、MI300X 和 MI355X）

对比 MORI EP 的 V1 和 V2 在 DeepSeek-R1 形状下的跨节点 dispatch/combine 性能，测了 MI308X、MI300X 和 MI355X 三种 GPU。第 1 节是测试配置，第 2 节是三种 GPU 的总体结论，第 3 节是各 GPU 的逐档数据。

## 1. 测试配置

### 1.1 共同的配置

- **形状**：256 个 expert，每个 token 选 8 个，hidden 7168。EP16：两台机器 × 8 张 GPU。
- **负载**：均匀路由，buffer 容量等于每次的 token 数，不带 scale，不量化。combine 为 BF16；dispatch 分别测 FP8 和 BF16。T 是每个 rank 一次的 token 数，测 4 到 4096。
- **kernel**：T ≤ 512 时比 LL kernel（V1 InterNodeV1LL 对 V2 InterNodeV2LL），更大的 T 比普通 kernel（V1 InterNodeV1 对 V2 InterNodeV2），与 V2 `internode_kernel="auto"` 的切换点一致；每一行都是同一族 kernel 之间的比较。
- **V1**：SHMEM 后端，`num_qp_per_pe` 为 2。这是 V1 调优脚本（`examples/ops/dispatch_combine/test_dispatch_combine_internode.py`）的默认值，V1 的调优表是在这个设置下调的；V1 API 的默认值是 1。几何参数来自 V1 的调优表，取法见 1.2。
- **V2**：HIP 后端，`num_qp_per_pe` 为默认的 8，几何参数和每档实际用的 QP 数（active QP）来自 V2 的调优表。
- **计时**：两边用同一套数据和正确性校验。每次测量 3 遍 ×（20 轮 warmup + 30 轮计时），每遍去掉第 1 轮，延迟取平均值。V1 和 V2 交替测 3 轮，每格取 3 轮的中位数；整段卡顿的运行剔除，判定和重测方式见 1.2。所有用到的运行都通过了正确性校验。
- **带宽口径**：与 V1 一致，都是每个 rank、每轮"字节数 / 时间"的平均值，不是网卡线速，两种口径的区别只在字节数怎么计。
  - **XGMI 带宽**按本 rank 收到的 token 计。
  - **RDMA 带宽**按 token × 目的节点计，含本节点；LL 时每个 token 计全部节点。两台机器时，其中真正跨机的约占一半。
  - 同一格两边搬的字节数相同，带宽的变化主要取决于耗时：同一行里 XGMI 和 RDMA 的变化相差不到 1.5 个百分点。

| 重测 | 判为卡顿的运行重测一次（这次 15 次） | 没过噪声门禁的格子重测，只有过了门禁的结果才替换（这次全部一次通过） | 同 MI300X（这次 V2 有 3 个格子重测了一次） |
| 测量时间 | 2026-11-04 至 11-05 | 2026-11-05 | 2026-11-04 |

- V2 的调优表在 `python/mori/ops/dispatch_combine_v2/tuning_configs/`，测量用的就是仓库里的这几张表。
- MI300X 上关闭了 NUMA 自动平衡（`kernel.numa_balancing=0`）。开着时，内核扫描进程内存会让 KFD 把进程在 GPU 上的队列整体驱逐约 17 ms，EP16 里任何一个 rank 被驱逐，所有 rank 都要等。V1 和 V2 都受影响，平均延迟会被明显拉高，表里可能出现"V2 更慢"的假象；带宽和中位数受影响小。
- 噪声门禁要求每个 phase 的平均值/中位数 ≤ 1.10、最大值/中位数 ≤ 5，三遍的 D+C 均值相差不超过 1.20 倍。

## 2. 总体结论

**V2 的 D+C 延迟比 V1 低多少：**

| GPU | dispatch | 小 batch（T4–T32） | 中 batch（T64–T512） | 大 batch（T1024–T4096） |
|---|---|---|---|---|
| MI308X | FP8 | 20%–31% | 14%–21% | 23%–39%，两次测量不一致，见 3.1 |
| MI308X | BF16 | 18%–32% | 11%–16% | 14%–20% |
| MI300X | FP8 | 36%–42% | 12%–22% | 25%–38%，V1 用的是借来的规则，见 3.2 |
| MI300X | BF16 | 35%–43% | 10%–22% | 11%–22% |
| MI355X | FP8 | 23%–30% | 12%–19% | 7%–17% |
| MI355X | BF16 | 21%–30% | 13%–16% | 9%–15% |

**大 batch（T1024–T4096）的带宽变化**（XGMI 口径，RDMA 口径相差不到 1.5 个百分点）：

| GPU | dispatch | dispatch 带宽 | combine 带宽 |
|---|---|---|---|
| MI308X | FP8 | +74% 到 +146%，两次测量不一致，见 3.1 | −1% 到 +23% |
| MI308X | BF16 | +5% 到 +48% | −4% 到 +24% |
| MI300X | FP8 | +89% 到 +127%，V1 用的是借来的规则，见 3.2 | +4% 到 +35% |
| MI300X | BF16 | +14% 到 +20% | +8% 到 +35% |
| MI355X | FP8 | +11% 到 +18% | +4% 到 +20% |
| MI355X | BF16 | +10% 到 +14% | +7% 到 +21% |

- **V2 在三种 GPU 的每一档都更快**，没有一格 V2 的 D+C 比 V1 慢。
- **小 batch 优势最大。** 小 batch 快 18%–43%；中、大 batch 一般快 7%–22%。MI308X 和 MI300X 的 FP8 大 batch 更高，但都另有原因：MI308X 两次测量不一致，MI300X 上 V1 用的是为 MI308X 调的规则。
- **小 batch 主要快在 combine。** 大 batch 上各机器不同：MI308X 和 MI300X 的 FP8 主要快在 dispatch；MI300X 的 BF16 和 MI355X 两个 phase 都快，分别快 8%–27% 和 5%–18%；MI308X 的 combine 除 T2048 外与 V1 相差不到 5%。
- **带宽只列大 batch。** 小 batch 受延迟限制，带宽的变化只是延迟变化的倒数。
- **一部分差距来自 V1 没调过的规则。** MI308X 和 MI355X 上 V1 的 BF16 dispatch 规则不全，MI300X 上 V1 的调优表只有 T ≤ 64 的 LL 规则，普通 kernel 借用的 MI308X 规则对 MI300X 偏小，见第 3 节。
- **这是 kernel 层面的对比，不是端到端推理。** 只测了这一个形状和均匀路由；真实负载的路由不均匀，dispatch 和 combine 之间还有 expert 计算。
