# 流量监控对 MORI EP 的性能影响和精度

本文测量 IO / EP 流量监控给 EP dispatch、combine 带来的开销，并把监控计的字节和硬件计数器对比。

三种配置，同一份源码：

| 配置 | 编译 | 运行时 |
|---|---|---|
| **OFF** | `BUILD_METRICS=OFF`：计数代码不编进 host 库和 JIT kernel | - |
| **ON，未启用** | `BUILD_METRICS=ON`（默认） | 不开监控 |
| **ON，启用** | `BUILD_METRICS=ON` | `MORI_METRICS_ENABLE=1`，每次调用都记 |

**结论**

- **ON，未启用**：只在 T = 128 的两处量得出：V1 节点内一对 dispatch + combine 多约 1 µs（+0.9%），
  V2 跨节点 `v2_ll` 多约 3 µs（+1.4%）。其余看不出。
- **ON，启用**：节点内每对多 4–7 µs，跨节点 T = 128 时多 9–14 µs。T = 128 时延迟 +3.5%–5.9%，
  带宽下降比例相近；T = 4096 时 0%–0.3%。
- 采样 `MORI_METRICS_SAMPLE_EP=8` 可把启用时的开销降到三分之一以下（第 5 节）。
- **精度**：监控计 payload。IO 字节和实际传输逐字节相等；RDMA 每块网卡和 mlx5 端口计数器只差 IB 包头
  （+0.6%–2.0%）；XGMI 链路字节是 payload 乘一个随流量形态变化的系数（1.14–1.61），同一负载下重复运行和 2 s 分片的波动都在 0.3% 以内（第 6 节）。

### 1.2 方法

| | 每种配置的运行次数 | 每次运行的计时样本 |
|---|---|---|
| V1 节点内 | 15 | 100 轮 × 100 次 graph 重放 |
| V2 节点内 | 15 | 1000 次 graph 重放 |
| V2 跨节点 | 10 | T = 128：20000 轮；T = 4096：3000 轮 |

## 4. 开销从哪里来

- **ON，未启用**：HIP kernel 每个计数点、shmem / cco 每次 put 各多一次判空；`EpArgs`、`GpuStates`、`ccoIbgdaContext`
  各多 8 字节。上面 1–3 µs 的差别应来自这些（未单独拆开量）。
- **ON，启用**：开销按 launch 算，不随 T 增长：
  - 每次 launch 在显存里做约 50 次原子加；
  - 一个线程在 launch 开始和结束时各读一次设备时钟；
  - combine 的计时线程等所有 block 报到后才取结束时刻；
  - launch 结束时把计数拷到映射到主机的镜像，host 只读镜像（不调 HIP，兼容 CUDA graph）；
  - 跨节点：计时从第一个 kernel 开始到最后一个 kernel 结束，最后一个 kernel 里每个 block 过一次 barrier；
    每次 RDMA put 对网卡计数做一次原子加。

## 5. 用采样降低开销

`MORI_METRICS_SAMPLE_EP=N`：每 N 对 dispatch + combine 记一对，按 N 次计，量级不变。运行中可通过监控端口的
`/sampling` 或 `mori.metrics.set_sampling(ep=N)` 修改，`ep=0` 暂停 EP 计数。

跨节点 `v2` 一对的延迟，相对"ON，未启用"（每格 2–4 次运行）：

| T | 1/1 | 1/8 | 1/64 | 暂停 |
|---|---|---|---|---|
| 128 | +4.4% | +1.5% | +1.2% | +0.8% |
| 512 | +1.0% | +0.2% | 0.0% | −0.2% |
| 4096 | +0.08% | 0.00% | −0.01% | −0.04% |

暂停后剩下的（T = 128 时 +0.8%）是通信库对 RDMA put 的计数，不受采样控制。

## 6. 精度：和硬件计数器对比

监控计 payload；网卡和 XGMI 计数器计线上 / 链路字节，多出协议开销。以下用 ON 构建、`MORI_METRICS_ENABLE=1`，两边取同一时间窗口。

### 6.1 RDMA：mlx5 端口计数器

**方法**：每台机器每 50 ms 读 `mlx5_0`–`mlx5_7` 的 `port_xmit_data` / `port_rcv_data`（单位 4 字节）和包数。
EP 运行时同时抓各 rank 的 `/metrics`，前后各读一次网卡计数夹住它；IO 每阶段前后留 2 s 空闲。
发送方向按源网卡和 `port_xmit_data` 比，接收方向按目的网卡和对端的 `port_rcv_data` 比。监控一侧的指标：
EP 用 `mori_gpu_rdma_bytes_total`（通信库每次 put），IO 用 `mori_io_nic_bytes_total`。

**负载**：EP V2 跨节点（`v2` T = 4096 / 128，`v2_ll` T = 128）；两节点间 IO RDMA，8 对 GPU 同时，
write 64 MiB、read 64 MiB、write 4 KiB 各 6 s。测量时节点 B 上有别人的节点内作业（不走网卡），只影响延迟，不影响字节对比。

**结果**（16 块网卡；差值相对监控，"每包多出"= 差值 / 包数）

| 负载 | 方向 | 监控 | 网卡（发送 / 接收） | 差值（发送 / 接收） | 每块网卡 | 每包多出 |
|---|---|---|---|---|---|---|
| EP `v2`，T = 4096 | A → B | 2789.731 GB | 2819.292 / 2819.575 GB | +1.06% / +1.07% | +0.88% – +1.24% | 25–26 B |
| | B → A | 2806.227 GB | 2836.831 / 2835.532 GB | +1.09% / +1.04% | +0.84% – +1.22% | 24–26 B |
| EP `v2_ll`，T = 128 | A → B | 522.662 GB | 528.892 / 528.920 GB | +1.19% / +1.20% | +1.16% – +1.28% | 26 B |
| | B → A | 520.917 GB | 526.957 / 526.822 GB | +1.16% / +1.13% | +1.02% – +1.28% | 25–26 B |
| EP `v2`，T = 128 | A → B | 538.042 GB | 544.833 / 544.816 GB | +1.26% / +1.26% | +1.24% – +1.30% | 26–27 B |
| | B → A | 539.361 GB | 545.922 / 545.902 GB | +1.22% / +1.21% | +1.19% – +1.23% | 25–26 B |
| IO write 64 MiB | A → B | 2199.023 GB | 2211.910 GB | +0.586% | 每块相同 | 24 B |
| IO read 64 MiB | B → A | 2062.658 GB | 2074.745 GB | +0.586% | 每块相同 | 24 B |
| IO write 4 KiB | A → B | 5.016 GB | 5.114 GB | +1.953% | 每块相同 | 40 B |

- 差的就是 IB 包头，每包 24–26 B（4 KiB 的 IO 为 40 B），包越满占比越小。发送端和接收端逐块对得上，说明流量记到了正确的网卡。
- IO 计到的字节等于笔数 × 每笔字节数。EP 按 token 算的 `mori_ep_rdma_bytes_total` 和通信库的 put 字节之比为 0.99996–1.00007
  （两者在 kernel 里更新时刻不同，窗口两端差几毫秒）。
- 在 AINIC（MI355X）上，`tx/rx_rdma_ucast_bytes` 计的是 payload，16 块网卡两个方向和监控逐字节相等。

### 6.2 XGMI：xgmi-netmon

**方法**：`xgmi-netmon record` 每 2 ms 读每块 GPU 在每条链路上的 `xgmi_write`。监控一侧 IO 用
`mori_io_completed_bytes_total{backend="xgmi"}`，EP 用 `mori_ep_xgmi_bytes_total{direction="tx"}`（每 0.5 s 抓一次）。
按同一窗口、同一条有向链路比较。各负载之间的空闲时段，8 块 GPU 所有链路合计 0 B/s，测量窗口里没有背景流量。

| 负载 | 监控（payload） | xgmi-netmon（链路字节） | 链路开销系数（netmon / 监控） | 各链路范围 |
|---|---|---|---|---|
| IO 单向 0 → 1，每笔 1 GiB | 49.4 GB/s | 57.9 GB/s | 1.172 | — |
| IO 单向 0 → 1，每笔 1 MiB | 43.6 GB/s | 49.5 GB/s | 1.136 | — |
| IO 双向 0 ↔ 1 | 98.1 GB/s | 117.6 GB/s | 1.199 | 1.1985 / 1.1986 |
| IO 56 对全互发 | 1908 GB/s | 2468 GB/s | 1.294 | 1.197 – 1.334 |

EP 节点内（8 rank，每格 3 次运行，各自单独录制；系数取 3 次的中位数，括号里是 3 次的范围；
"2 s 分片波动"是一次运行内按 2 s 切片后比值的标准差，取 3 次中最大的）：

| 负载 | 监控（payload） | xgmi-netmon（链路字节） | 链路开销系数 | 各链路范围 | 2 s 分片波动 |
|---|---|---|---|---|---|
| EP V1，T = 4096 | 1954–1983 GB/s | 2835–2875 GB/s | 1.4509（1.4497–1.4510） | 1.434 – 1.469 | 0.18% |
| EP V2，T = 4096 | 2170–2174 GB/s | 3136–3142 GB/s | 1.4454（1.4452–1.4457） | 1.432 – 1.462 | 0.23% |
| EP V1，T = 128 | 730–760 GB/s | 1171–1219 GB/s | 1.6052（1.6040–1.6053） | 1.516 – 1.754 | 0.27% |
| EP V2，T = 128 | 1236–1268 GB/s | 1836–1884 GB/s | 1.4857（1.4853–1.4893） | 1.397 – 1.615 | 0.28% |

每次运行前链路空闲都是 0 B/s。

**这个系数不是监控的误差。** 为了确认，用一个不经过 mori 的小程序做对照：每块 GPU 上的 kernel 用 16 B store
直接写对端显存，写入的字节数精确已知，在 xgmi-netmon 下测同样的系数：

| 对照：kernel 直接写对端显存（字节数已知） | payload | 链路开销系数 | 各链路范围 |
|---|---|---|---|
| 单向 0 → 1 | 49.1 GB/s | 1.229（反方向链路另有 1.08 倍 payload） | — |
| 双向 0 ↔ 1 | 93.3 GB/s | 1.297 | 1.297 |
| 56 对全互发，打满 | 2169 GB/s | **1.453** | 1.414 – 1.500 |
| 56 对全互发，每块 GPU 只用 7 个 block | 609 GB/s | 2.591 | 2.571 – 2.617 |
| 56 对全互发，每次每个对端只写 16 KB | 23 GB/s | 2.944 | 2.830 – 3.039 |

- 8 卡全互发打满时，纯 kernel 写的系数是 1.453，和 EP T = 4096 的 1.445–1.451 一致；流量越稀，系数越高（2.6–2.9），
  EP T = 128 的 1.49–1.61 落在两者之间。所以 EP 上的系数来自 XGMI 链路对 GPU store 的计数方式，监控没有少计。
- 单向 kernel 写时，反方向链路上也有约 1.08 倍 payload 的字节，没有任何数据往回走，这部分是写的响应 / 协议流量；
  两个方向都有 payload 时，它叠加在对方的 payload 方向上，这就是全互发时系数比单向高的原因。

- 链路字节 / payload 随流量形态变化（1.14–1.61），没有固定换算系数，所以 XGMI 上不比绝对字节。
  同一负载下系数很稳：重复运行之间差 0.3% 以内，一次运行内 2 s 分片的波动在 0.3% 以内，两者同步变化。
- 单向流量时反方向链路上也有协议流量（IO 的 SDMA 拷贝约 0.57 倍 payload，kernel 写约 1.08 倍），监控不计。
- 监控的 payload 本身是准的：IO 逐字节相等；EP 每个 token 发往其它 rank 的份数计到 4.916–4.933，按路由期望 4.9315。
